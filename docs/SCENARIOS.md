## Three outcomes, one scenario

The API preserves original actions under original assumptions (A), frozen decisions under scenario assumptions (B), and newly calculated actions under those same scenario assumptions (C). Changes always start from a deep copy of the immutable sample. Existing cached samples are never modified. Drafts/results live only in the current React session, without local storage, a database or durable server state.

B and C share the same prepared demand arrays, buffers and transformed dataset. The planning entry point accepts these prepared forecasts internally; public planning requests still use the unchanged forecast pipeline. The two-second best-effort optimizer, 30-second per-plan budget, objectives, tolerances and independent replay are unchanged. Scenario comparison reserves the remaining part of a cooperative 30-second comparison budget for planning after preparation. No complete plan response is cached.

`feasible_fallback` remains a validated constrained fallback, never global optimality. Original snapshots and frozen decisions are labeled as independently validated policies rather than newly optimized plans. Replanning can return structured input/hard-constraint failures with no executable plan.

## Definition and composition

Definitions are normalized by sorting each change collection. The SHA-256 scenario identifier includes the baseline action snapshot identifier, normalized definition and canonical dataset/demand/buffer assumptions. Forecast versions combine the series projection hash, selected method, policy buffer and scenario daily demand. All identifiers are returned in summary/detail responses. Duplicate or overlapping changes are rejected, including cross-scope demand overlaps on a SKU/store/day, repeated supplier delays, overlapping supplier availability dates, and duplicate budget weeks. Unknown identifiers, nonfinite/negative amounts, sub-cent funding values and unsupported dates are rejected.

- **Demand:** SKU, category or store; inclusive dates within days 1–56; 0–500% uplift. Multiply the existing expected forecast once by `1 + percent/100`. Existing known-event effects remain in that underlying forecast; scenario uplift is an additional explicit future adjustment. Do not add scenario events to historical training or evaluation. Empirical historical-error buffers retain the existing policy; days-of-demand fallback buffers use the adjusted visible demand. Both B and C use exactly that same buffer.
- **Selected existing supplier receipts:** only explicitly selected, unreceived order IDs belonging to the selected supplier move. Add the requested days to their original arrival, then advance to an open destination receiving day. Other orders and supplier capacity are unchanged. Current Payables contain fixed contractual due dates with no receipt-dependent field, so their amounts/dates stay fixed and are counted once.
- **Future purchasing paths:** an explicit checkbox applies the selected supplier's additional lead days to all new orders within the 56-day horizon. It does not select existing inbound orders implicitly. Offer/order/dispatch calendars remain unchanged; receiving calendars and new receipt-relative balances apply. New deposits stay at the unchanged order date. Frozen purchase quantities, order decisions and identities are preserved while derived receipt dates move. Lead times over 14 days, protection envelopes over 28 days, or a selected existing/frozen receipt beyond day 56 are explicitly rejected. Future candidate purchases that cannot arrive within the horizon remain ineligible under the existing engine; no delay is shortened.
- **Remaining availability:** selected supplier and inclusive dispatch dates, with 0–100% remaining. Floor each dated SKU availability to an integer unit. This changes remaining availability for *new* purchases; confirmed inbound and shared supplier ceilings are untouched.
- **Funding:** explicit existing weekly dates with optional new-purchase commitment authority and/or payment ceiling in SAR cents. Omitted fields retain baseline values. Movement allowances and existing obligations are unchanged. A ceiling below existing payables causes explicit infeasibility, not removal of obligations.

Changes compose in separate dimensions: receipt/lead changes, availability reductions and funding limits transform the dataset; demand changes apply once after underlying forecast preparation. If future paths alter protection days, forecasts/buffers are reevaluated with the unchanged evaluator. Otherwise that preparation is reused safely within the request. A reset clears the definition and restores the original snapshot, rather than reversing accumulated mutations.

Promotion, Supplier disruption and Tighter funds populate ordinary editable controls. Applying another preset replaces that preset's change family while preserving other families. The disruption preset explicitly lists both its selected existing late receipt and the separate supplier-availability loss. Tighter funds starts with zero new commitment authority and unchanged payment ceilings; both are editable. Presets contain no calculated recommendations.

## Infeasible frozen actions

The existing independent replay detects unavailable donor stock, early transfers, supplier capacity breaches, calendar and funding failures. Its diagnostic traversal can contain negative stock or downstream receipts from impossible dispatches when checking invalid actions. Therefore **all aggregate outcome metrics, service detail, daily stock and related deltas are unavailable for any infeasible policy**. Invalid internal traversal values are never presented as fulfilled service, inventory or savings.

Frozen actions remain visible unchanged (except explicitly derived delayed purchase dates), alongside scoped failures. Cash and payments remain visible as **attempted contractual obligations**, with negative headroom exposed. For a replanned policy to be executable, independent replay must pass; otherwise its metrics are likewise unavailable. Underlying expected-demand forecasts remain inspectable even when the action policy fails.

Shock deltas are B − A. Replanning deltas are C − B. Fill deltas use percentage points; other deltas use their stated units/SAR. No invalid comparison is called an improvement. Additional service per extra SAR is omitted; there is no efficient-frontier claim. Action differences match purchase SKU/supplier/offer/destination/order date or movement SKU/source/destination/dispatch date, ignoring generated IDs and generic reason text. Changed quantities and receipt dates are displayed.

## Stateless transport and evidence

- `POST /api/scenarios/baseline` accepts only sample size and calculates a live baseline once.
- `POST /api/scenarios/capture` accepts the already displayed Plan Review's actions and dataset hash. It independently replays them and issues the same compact baseline identifier without rerunning optimization.
- `POST /api/scenarios/compare` accepts a compact baseline action snapshot plus a definition. It reconstructs the sample, checks the snapshot's dataset/version/checksum, independently replays the original actions, and evaluates B/C. It returns actions, summaries, cash, failures/shortages, deltas and versions—not three complete PlanResults or any daily stock ledger.
- `POST /api/scenarios/detail` accepts that same baseline/definition and the selected policy's actions/hash where needed. It reuses the submitted calculated decisions, reconstructs canonical assumptions and independently replays the complete network, then returns all 56 days at all locations for the selected SKU, relevant receipts/movements/payments, complete weekly cash, shortages and its actual evaluated store forecast. It does not optimize again. The selected SKU/store version reconciles with the comparison's forecast version map.

The action snapshot is internal request transport, not a portable export or accepted plan. Its checksum detects mismatched/modified content; it is **not a cryptographic signature or authentication guarantee**. Supplied decisions are untrusted and independently replayed. This private synthetic demo has no execution authority. Future changes to calculation semantics must bump the snapshot version. No server process memory must survive between requests; only reproducible input generation may be cached. No historical rows or baseline daily ledgers are sent back by the browser.

Evidence identifies baseline, scenario, policy, assumption hash, action hash and forecast version. Purchases and movements draw from pooled SKU/location stock: related receipts are not invented one-to-one dependencies. Grouped movement fees are shown once in the payment ledger for the whole lane/date group, not attributed as a per-SKU charge. Action detail shows the original forecast and dated scenario quantities separately, retaining historical evaluation/censored observations. Demand Review can open that exact selected evidence.

Requests share the existing semaphore. Browser aborts invalidate rendering but cannot interrupt a running Python calculation; the scenario client honors 429 Retry-After while checking its abort signal. Editing controls clears the displayed comparison and shows a draft notice; dataset changes/reset clear obsolete detail and abort pending requests. No late response can overwrite the new selection.
